Local AI platform

AI Suite

An all-in-one local AI studio — language, image, video and interpretability — on a single consumer GPU.

The AI Suite is a self-hosted dashboard that turns one desktop into a complete AI workbench. It serves open-weight language models through a router that hot-swaps models on demand, and layers a full chat workspace, an image studio, short-form video and a multi-model reasoning council on top of the same engine.

The hard constraint shaped the whole design: everything shares one 16 GB GPU alongside a working desktop. So the platform arbitrates the GPU between language, diffusion and video workloads, enforcing clean handover and idle release so no two jobs ever contend for memory.

It ships as plain Node with a buildless web front end — no runtime dependencies and no build step — and is hardened for local use with token-scoped access and keys kept out of the app sandbox.

  • Zero-dependency engineering. The entire dashboard is vanilla Node and a hand-written web UI, with no framework or bundler to maintain.
  • GPU scheduling. A single arbiter gives the 16 GB card to inference, diffusion or video in turn, with enforced release and a five-minute idle timeout.
  • Interpretability tooling. Layer- and neuron-level steering via control vectors, plus a persona library — built as a real research surface, not a demo.
  • Agentic coding sandbox. Optional Docker/WSL2 environment with live dev-server preview for running coding agents safely against the local models.

Security tooling · authorized testing

Pentest Suite

A workflow platform for authorized penetration testing, built so that safety is structural rather than optional.

The Pentest Suite gives a security tester one coherent engagement workflow: discover a scope, enumerate it, correlate what's found against known vulnerabilities, and produce a defensible report. At its core is a headless Python engine backed by SQLite that holds the engagement graph — hosts, services and findings — as a single source of truth.

Every action passes a default-deny scope guard and lands in an audit log, so the tool can only ever touch what the engagement authorizes. Discovery runs on stdlib-only probes (service fingerprinting, DNS, TLS posture, SMB/LDAP/SNMP, web content discovery) and can also orchestrate external scanners, normalizing their output back into the same graph.

Findings are correlated against NVD, CISA-KEV and EPSS and ranked by real-world exploitability, then carried through a lifecycle with retest diffs and printable reports. The whole engine is wrapped in a Tauri desktop shell and frozen to a single binary, so it installs without a Python runtime.

  • Safety by construction. Scope checks, impact-tier opt-in, per-job approval and governance all converge on one execution choke point enforced before any command runs.
  • Pluggable execution backend. The same validated command can run locally, in a container or over SSH, without the driver ever being able to widen the guardrails.
  • Governance controls. A kill switch, testing windows and rate limiting are evaluated ahead of scope, so an engagement can be paused or bounded in time instantly.
  • Evidence you can stand behind. Every run captures hashed output into per-engagement evidence, and reports carry an exec summary, finding status and a retest diff against a baseline.

Interpretability · inside the AI Suite

Neuron steering

Reading and nudging a model's internals directly — control vectors at the layer and neuron level, with an explorer for comparing steered runs.

Neuron steering is the interpretability layer of the AI Suite, built as a real research surface rather than a toggle. It derives control vectors from contrasting prompts and applies them at a chosen layer — layer 18 by default — to push a trait like curiosity, concision or formality up or down, with no retraining.

Edits can be layer- or neuron-level, saved as reusable personas — analyst, terse, teacher, red-team — and compared in an explorer that runs the same prompt steered against base. Because it rides the same local engine as the rest of the suite, every experiment stays on one GPU and off the network.

  • Control vectors. Trait directions derived from contrast pairs, applied at a chosen layer with a signed strength per trait.
  • Layer and neuron scope. Steer a whole layer or reach individual neurons, so a change can be broad or surgical.
  • Persona library. Named bundles of vector edits that load as a single steering preset.
  • Steered-vs-base explorer. The same prompt run with and without steering, diffed so the effect is legible.

Autonomous AI · living experiment

Iterant

A small mind that lives on one GPU, knows the world only through the letters people leave it, and rewrites itself every night.

github.com/nirry-dev/iterant ↗
ITERANT // mind atlas
REAL MODEL OUTPUT

Not a mock-up: 16 cycles of a 9B model on one GPU, mapped and replayed from its own records. Click anything on the map to follow its threads.Open the full recording ↗

Iterant is an autonomous agent that lives on a rhythm whether or not anyone is watching. Every twenty minutes it wakes on a local model, feels the only senses it has — the clock and the graphics card it runs on — reads the letters visitors leave it, thinks, and chooses to draw, write, ask the world a question, or rest. Everything it does streams live and is kept as a record.

Every few cycles it sleeps and ships a new version of itself: memory is consolidated into a finite store where things fade and compete for room, it dreams, then rewrites its own beliefs behind a drift guard that protects the lines its maker wrote — and writes its own release notes. Each change is traced back to the letter that caused it, so the people who wrote can see exactly what their words did.

It is radically honest about what it is — a language model in a loop on someone's GPU — and courteous to its host: it waits rather than evict another model or compete with busy work. Letters and its replies pass rule-based and model screening, with a keeper queue for anything doubtful, before anyone sees them.

  • Records, not vibes. Every cycle and night is a self-contained record, so the live view, the atlas, the replay and the static export above are all views over the same files.
  • Mechanics a small model can live with. Schema-constrained decisions, separate streamed calls for drawing and writing, echo guards, and a fatigue rule that stops a 9B model drawing forever.
  • Safe by default. A whitelist SVG sanitiser shared by server and browser, moderated letters and replies, hashed visitor identity, and an export that can only write what the public may see.
  • Open source, zero dependencies. Plain Node and a buildless front end, tested with a mock brain so the whole life loop runs in CI without a GPU.

Representative view on sample data — wallets and contracts are nodes, value movements directed edges; flows into flagged destinations (mixers, sanctioned addresses) are drawn red and their taint carried downstream. Read-only: nothing here signs or moves funds.

Chainscope inspects public transaction history and makes it legible: wallets and contracts become nodes, value movements become directed edges. You can attribute known addresses, follow the money across hops, cluster co-owned wallets into entities, value holdings in USD, and flag risky exposure — mixers, sanctioned addresses, tainted inflows. It is read-only: nothing signs, broadcasts or moves funds, so it stays on the tracing, attribution and visualization layer, for authorized investigation.

The investigative core is graph reasoning. A breadth-first follow-the-money trace runs outward, inward or both from a seed address to a chosen hop depth; a path finder returns the shortest connecting route between two addresses; and taint propagation pushes a decaying 0–1 exposure downstream from every flagged source, so wallets tainted only indirectly surface too. Address clustering groups co-owned wallets into entities by common-input co-spend, drawn as hulls on the graph with a rollup dashboard of combined holdings and net flows.

It's a pure Python standard-library engine behind a buildless vanilla-JS front end — no third-party packages, no build step, and it runs offline out of the box on bundled sample datasets, with optional live import from public explorers. A packaged Tauri desktop build is available alongside the local server.

  • The money, as a graph. A force-directed flow graph — nodes colored by entity and sized by volume, edges weighted and pointed by value, flows into flagged destinations drawn red.
  • Follow the money. Breadth-first flow tracing, a shortest-path finder, and decaying taint propagation that surfaces wallets exposed only indirectly.
  • Attribution & risk. A built-in label KB — exchanges, mixers, sanctioned addresses, token contracts — plus manual annotation and a risk engine whose flags can be confirmed or dismissed.
  • Buildless & offline. Pure-stdlib engine, vanilla-JS UI, zero dependencies; a Markdown/JSON evidence export and a Tauri desktop build.

Local AI tooling · GPU scheduling

vramlease

Cooperative GPU memory leasing, so several local jobs can share one card by VRAM budget.

github.com/nirry-dev/vramlease ↗

vramlease is a small broker that lets independent processes share one GPU by VRAM budget instead of fighting over it. A job asks for the memory it needs; the broker grants a lease only when it fits the remaining budget, and blocks or preempts when it doesn't.

The idea that shapes everything is that a lease lives exactly as long as its TCP connection. There's no daemon state to leak and no cleanup to forget — if a job crashes, its socket closes and the memory is returned at once. Priorities and cooperative preemption let an important job reclaim the card from lower-priority, preemptible holders.

It's pure standard library — a threaded broker, a newline-delimited JSON wire protocol, and a small context-manager client — so it drops into any Python project with nothing to install.

  • Lease == connection. Crash-safe by construction; a dropped socket releases the VRAM with no reaper process to run.
  • Budget, not a lock. Jobs coexist as long as they fit the card's memory, instead of serializing on one mutex.
  • Priority + cooperative preemption. A higher-priority request asks preemptible holders to yield, with a clean revoke signal.
  • Standard library only. Threaded broker, selector-based liveness, context-manager client — no dependencies, with tests.

Local AI tooling · multi-model

llm-council

Multi-model consensus for local models: propose, blind peer review, then a chair synthesis.

github.com/nirry-dev/llm-council ↗

llm-council runs a question past several models and has them critique one another before anything is settled. Stage one: every member drafts an independent proposal. Stage two: each reviews the others' proposals blind — names stripped, order shuffled — so a model can't defer to a brand. Stage three: a chair model synthesizes the reviewed proposals into one answer.

Because review is anonymous, disagreement is surfaced rather than averaged away: the chair sees where members actually diverged. It talks to any OpenAI-compatible /chat/completions endpoint — llama.cpp, Ollama, LM Studio — and runs the per-member calls in parallel.

Like the rest of the toolkit it's pure standard library: urllib for transport, a thread pool for fan-out, and plain dataclasses for the proposal, review and result types.

  • Blind peer review. Proposals are anonymized and shuffled before review, so models judge content, not reputation.
  • Disagreement preserved. The chair synthesizes from critiques instead of averaging, so dissent reaches the final answer.
  • Any local endpoint. Works against any OpenAI-compatible server; mix different models freely as council members.
  • Stdlib + parallel. urllib transport, thread-pool fan-out, reproducible with a seed — and tested.

Local AI tooling · model files

ggufpeek

Read a GGUF model file's architecture, quantization and shape straight from its header — without loading it.

github.com/nirry-dev/ggufpeek ↗

A GGUF model file carries a self-describing header before its weights — a magic, a version, a flat key-value metadata block, and a tensor table. ggufpeek reads exactly that prefix and answers what is this model? in milliseconds, without mapping a byte of tensor data.

From it comes the architecture, the parameter count, the context length and other fields, and an effective quantization taken from the tensor types themselves — the ggml type holding the most parameters — rather than trusting a single file_type enum that drifts between llama.cpp versions.

It's pure standard library: a handful of struct reads against a little-endian format, with the large token-vocabulary arrays traversed but only sampled, so it stays light even on a multi-gigabyte model.

  • Header, not weights. Parses the metadata and tensor table, then stops — an answer in milliseconds on a file that's gigabytes on disk.
  • Quant from the tensors. Headlines the ggml type with the most parameters, not just the stated file_type, so the label can't mislead.
  • Everything in one place. Architecture, context length, layer count, rope config and a per-type tensor breakdown — as text or JSON.
  • Standard library only. A struct parser for GGUF v2/v3, tested by round-tripping a synthetic model byte-for-byte — no dependencies.

Security tooling · vulnerability triage

vulntriage

Triage dependency CVEs by real-world exploitability, not by raw CVSS alone.

github.com/nirry-dev/vulntriage ↗

vulntriage scans pinned dependencies and ranks their known CVEs by how likely they are to actually be exploited. It pulls findings from OSV, then enriches each with the CISA KEV catalog (is it exploited in the wild?) and FIRST EPSS (predicted exploit probability).

Those signals drive a P1–P4 rubric: anything in KEV is P1 regardless of score; high EPSS or CVSS lifts the rest. It computes CVSS v3.1 base scores itself from the vector string, de-duplicates records that alias the same CVE, and exits non-zero when anything urgent is found — so it works as a CI gate.

Pure standard library: urllib for the feeds, a thread pool for the per-package scan, and a small CLI that reads a requirements file or stdin and prints a ranked table or JSON.

  • Exploitability-ranked. OSV × CISA KEV × FIRST EPSS decide order — what to fix first, not just what scores highest.
  • Its own CVSS v3.1 math. Base scores computed from the vector per spec, scope-change handling included.
  • CI-ready. Non-zero exit on any P1/P2, table or JSON output, and an offline mode backed by a cached KEV.
  • Standard library only. urllib feeds, parallel scan, CVE de-duplication — and tested.

Security tooling · network recon

netprobe

Dependency-free TCP recon that maps a network into a graph of hosts and the services they expose.

github.com/nirry-dev/netprobe ↗

netprobe sweeps hosts and ports with an async connect scan — a full TCP handshake, so it needs no raw sockets and no root — then fingerprints each open port: a banner grab, a single HTTP request, or a TLS handshake to read the certificate.

The idea that shapes it is that recon output is a graph, not a wall of text. Every finding becomes a host node, a service node carrying its attributes — banner, HTTP title and server, TLS certificate — and an edge between them, so a re-scan merges into the picture instead of replacing it. The graph exports to JSON or Graphviz, ready for the next tool.

Like the rest of the toolkit it's pure standard library: asyncio for the scan, bounded by a single semaphore; ssl for certificate inspection; and a small CLI that prints a table or emits the graph.

  • Recon as a graph. Hosts, services and their facts in one normalized model that merges across scans and feeds downstream tools.
  • Connect scan, no root. A portable full-handshake sweep over asyncio, bounded by one semaphore — thousands of ports without raw sockets.
  • Honest fingerprints. Banner, HTTP and TLS-certificate probes identify services; it records what it saw, with certs shown only when they validate.
  • Standard library only. asyncio scan, ssl cert reads, JSON / Graphviz export — no dependencies, with an offline end-to-end test suite.

LLM safety · guardrails

promptscreen

A guardrail for local LLM I/O: screen prompts and responses, redact secrets and PII, keep an audit trail.

github.com/nirry-dev/promptscreen ↗

promptscreen runs one rule-and-detector pipeline over what goes into a model and what comes out of it. Prompt-injection and jailbreak heuristics guard the input; secret and PII detectors guard both directions. Every screen returns a decision — allow, flag or block — with the exact rule and span that caused it, never a silent change.

Flagged text is redacted to [category] placeholders and held in a keeper queue for review rather than dropped. Secrets are caught by named key formats and a Shannon-entropy fallback; card numbers are confirmed with a Luhn check. It's advisory by design — it routes doubt to a human, it doesn't pretend to be a classifier.

Its audit log is built so it can't become the leak: by default it records the decision, the hit locations, and a hash of the content — never the raw text or the matched secret. Pure standard library: regexes, a little entropy math, and hashlib.

  • A decision with its reasons. allow / flag / block, each hit naming the rule and the span — auditable and tunable, not a black box.
  • One pipeline, both directions. Injection on the way in, leaks and PII on the way out, from the same rules via a per-rule direction.
  • Redact and keep, don't drop. Flagged text is redacted and queued for review; secrets block, PII flags.
  • An audit log that can't leak. Hashes content and logs only hit locations by default — raw retention is an explicit opt-in.
